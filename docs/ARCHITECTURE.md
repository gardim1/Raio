# Raio architecture (v1)

Status: **approved by the owner on 2026-10-01, with adjustments** (recorded below). This document records the approved technical direction; it is not evidence that anything described here is implemented. See `docs/STATUS.md` for what actually exists and was verified.

## Sources and precedence

- The approved design is a design-canvas export (`Raio.dc.html` + `raio-engine.js` + a generated design-tool runtime). It is used as the **visual and behavioural reference** for the central app only. Its runtime is not shipped.
- The handoff prototype (React + TypeScript, with a pure frame engine, a replay compiler and tests) is the **code base** that is ported.
- Precedence when they disagree: approved design export for visuals and central-app behaviour; prototype for engine/code; the semantic corrections in this document override both.
- Design reference material stays local in the ignored `.local/design-reference/` directory and is not published.

The prototype's outer review chrome (mode dock, concept film, states gallery, desktop backdrop, keyboard 1-5 shortcuts) and the export's review sidebar (mode tabs, scenario buttons, state presets, editor props for OS chrome and island dock) are **not product navigation**. They live in a separate, labelled development harness entry.

## Shape

```
Claude Code hook (command, async) -> raio-hook binary -> inbox/<ts>-<rand>.json  (minimised, atomic, capped)
filesystem watcher + git status ---------------------------------+
                                                                 v
Rust core (I/O and durability only): ingest -> validate -> dedupe -> SQLite (WAL, app data dir)
                                                                 | typed Tauri IPC
                                                                 v
TypeScript renderer (all semantics): projection (paths -> areas, validation, staleness)
   -> map + notices + timeline | compileReplay(session) -> evaluateFrame(t) -> SVG
   Surfaces: Expanded | Mini Player | Island      (dev harness = separate Vite entry)
```

- **Desktop shell: Tauri v2.** The renderer is plain web React; on Windows (first target) WebView2 is Chromium-based. A Rust workspace provides a small, fast hook binary, a native filesystem watcher and bundled SQLite without Node native-module ABI rebuilds. Resident memory/CPU are to be measured, not assumed.
- **Rejected alternative: Electron.** Real advantages: identical Chromium on Windows and macOS and `setIgnoreMouseEvents(..., {forward})` for the Island. Rejected because a light hook would need a third runtime or a full Electron launch per tool call, native SQLite/watcher modules need ABI rebuilds, and it bundles its own Chromium and Node into an always-on utility. It remains the documented fallback if the native Windows gate fails; switching requires owner approval.
- **Shell-independent renderer.** The renderer talks to a `DesktopBridge` port with a fixture adapter (browser, tests, harness) and a Tauri adapter.
- **No** cloud backend, login, LLM API, loopback HTTP server, Python, Node sidecar or plugin marketplace.

## Event contract v1

```
{ schema: 1, id, source: 'claude-hook'|'fs-watch'|'git-status'|'fixture',
  provenance: 'agent-reported'|'filesystem-observed'|'fixture',
  attribution: 'session'|'unassigned',
  projectId, sessionId?, agent: 'claude'|'codex'|'unknown', subagentId?,
  sourceAt?, observedAt, seq, kind, paths: string[], evidence: { toolUseId?, toolName?, exitCode?, commandClass? } }
```

- Kinds: `session.started`, `session.ended`, `turn.ended`, `file.inspected`, `file.edit.attempted`, `file.edit.reported`, `file.edit.failed`, `file.changed`, `command.observed`, `command.result` (only with a captured exit code).
- `id` is deterministic from (source, session id, tool-use or prompt id, hook event name); otherwise a UUID generated by the hook. Claude Code hooks provide no per-event id or sequence number.
- Paths are stored project-relative (POSIX). **Area/node ids are not persisted**; grouping is a projection, so user corrections re-project history.
- Not stored by default: prompts, file contents, tool responses, transcripts, full command strings. Only a command class (`test|build|migration|install|other`) and program name, with token-like strings redacted.

## Ingestion and persistence

- The hook writes a temp file in `inbox/.tmp` and renames it into `inbox/` (same volume). Over a file/byte cap it drops the event and leaves a marker so the UI can show lost events. It exits 0 within ~2 s on its own (whether Claude Code times out async hooks is to be verified). **The hook never writes raw stdin**: unknown or malformed input is dropped and counted; only minimised records reach disk, and paths outside the project become `outside-project`. Inbox files are deleted only after the database commit.
- Raio closed: the inbox accumulates up to the cap and is ingested on next start.
- Dedupe by primary key `id`. Ordering by `sourceAt`, then ingestion `seq`; skewed clocks are flagged.
- One SQLite file (WAL) in the app data dir: `events`, `sessions`, `projects`, `meta`. Embedded migrations are applied at startup and reported as applied (via `user_version`), never as merely created. Default retention 30 days, per-session cap, "Clear history". A corrupted database is renamed aside, never silently deleted, and the UI shows that history is unavailable.
- The inbox is ordinary files in the user's profile: any process running as the same user can write there. Events are untrusted input, validated and size-limited. This is not OS-level isolation.

## Evidence and validation semantics

- Kept distinct: inspected vs edited; attempted vs reported vs confirmed-on-disk edit; migration file added vs executed; dependency manifest changed vs installed; test command observed vs result captured; `passed | failed | not-run | unknown | incomplete | stale`; session-attributed vs `unassigned` change.
- A reported edit whose path also changes on disk within a window on either side is "reported and consistent on disk": consistency, not proof of authorship. A concurrent unassigned change on the same path lowers confidence. A filesystem change without a matching reported edit is `unassigned` ("changed in project, author unknown").
- A passing result followed by any non-ignored disk change (whoever made it) or a later reported edit becomes `stale`. A failure is never turned into `stale`: it stays visible as a failure, annotated "code changed since" when the project changed afterwards. Results are kept as history: the replay shows each result with the status it had when it happened, and a pass becomes `stale` as a later transition at the change time. A `running` validation without a result becomes `incomplete` at session end; a session without an end event is `incomplete`.
- The Rust core only records facts (hook events, debounced `file.changed`); matching reported edits to disk changes, staleness and grouping are pure TypeScript projections over the persisted events (`src/features/project/`), so corrections re-project history.
- Raio never runs project tests, migrations or commands to turn a status green.

## Map meaning

- Nodes: heuristic directory-convention groups (workspace packages, conventional folders, top-level fallback), max 12 + "Other", labelled heuristic and user-correctable.
- Edges: only static import relations between groups for TS/JS (lightweight import/require scan), labelled heuristic. Other languages show "relationships unknown"; no invented edges.
- Activity trail is a separate layer. The orb travels along an edge only when the edge exists; otherwise it uses the design's jump. **The trail never creates or reveals an edge.** Node positions are persisted; no continuous relayout.

### Semantic corrections to the approved design (visual language kept)

- "Frontend now calls Auth" / edge reveal during replay only with an existing static edge; otherwise factual copy ("Frontend: 1 file edited").
- "Unexpected area touched" only for paths the user marked out of scope; the automatic "unconnected system" heuristic is removed from v1.
- "Public API changed" is out of v1.
- "Migration detected" becomes "migration file added"; "executed" requires an observed command with a captured result.
- "New dependency added" becomes "dependency manifest changed"; "installed" is a separate state.
- Overlapping subagents/turns activate together labelled "in parallel"; no invented causal chain.

## Replay

Same event/state model, `evaluateFrame` and components as the live UI. Idle and repetition are compressed; failures, warnings, failed/stale validations and sensitive-file changes are never dropped (dense events become a grouped notice; the full list stays in the inspector). Deterministic, seekable clock; reduced-motion uses the stepped mode; animation pauses when hidden.

## Integrations

- **Claude Code** (first): opt-in "Connect this project" writes `<project>/.claude/settings.local.json`, shows the diff, backs up, preserves existing hooks, marks Raio entries and removes only those on disconnect. Command hooks, `async: true`, pointing to the absolute `raio-hook` path. The connection is bounded in time (the hook is inert when Raio's heartbeat is stale; the inbox has a TTL), the user is warned if the settings file is not git-ignored, and hooks apply to new sessions. No global settings. Called "supported" only after contract tests with payloads recorded from the installed version.
- **Codex** (later, same adapter boundary): current documentation describes native hooks (project `.codex/hooks.json`, trust via `/hooks`), preferable to reading session rollouts. Not verifiable on the reference machine yet.

## Testing layers

Domain and contract tests (Vitest), core tests (`cargo test`), integration (hook binary -> inbox -> DB -> projection), renderer visual tests (Playwright, deterministic clock), a native Windows checklist recorded only when actually performed, and macOS build CI labelled "builds", not "validated".

## Guideline consultation and justified deviations

The organisation-administered policy of the assistant account requires consulting a generic architecture router before generating code. It was consulted once as advisory guidance on 2026-10-01. This does **not** make Raio an organisation project; Raio's `AGENTS.md` and this approved architecture prevail. Deviations from those generic defaults:

| Generic default | Raio decision | Reason |
|---|---|---|
| Separate repositories per layer | One repository | Raio is a single desktop app; the Rust core is an in-process native layer, not a networked backend. |
| Tailwind + shadcn/ui | Plain CSS + token CSS variables | Pixel fidelity to the approved design; tokens map 1:1. |
| TanStack Router/Query | None | No server and no routes; surfaces are windows. |
| React Hook Form + Zod | None for now | No forms in v1 scope; IPC payloads use small typed guards. |
| Token/auth baseline | Not applicable | No login or accounts. |
| Docker/compose reproducibility | README + pinned versions + lockfile + Rust toolchain file | Native desktop app; containers do not exercise windows/tray. |
| OTEL observability | Local structured logs only, no telemetry | Local-first privacy requirement. |
| develop/staging/main branching | Small local commits per `AGENTS.md`; no push without owner approval | Owner's repository policy. |

Kept: feature-first structure, English identifiers, tests first for domain logic, Vitest + Playwright, coverage as a signal.
